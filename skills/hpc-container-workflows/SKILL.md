## Goal

Help the user choose a container workflow when repeated installs, startup load,
or native system libraries make a plain module-plus-venv or module-plus-library
install a poor fit. This skill is about the build workflow, not language-level
package discovery.

Use the language-specific package skills first when needed:

- `hpc-python-packages` for Python dependency discovery and install planning;
- `hpc-r-packages` for R package discovery and install planning.

## Workflow

When a project should move into a container:

1. identify the package stack and any native/system dependencies with the
   language-specific skills;
2. decide whether the container should be built from an Apptainer definition
   file or from a generator such as `hpccm`;
3. stage the recipe in a project directory or remote project space, not in a
   long-lived scratch location;
4. build in a Slurm job when the recipe is large, the build is expensive, or
   login-node load would be annoying to other users.

## HPCCM Regeneration Rule

If the Apptainer definition is generated by `hpccm`, regenerate it before every
build. Treat the generated definition as a build artifact, not a source file.
A stale recipe is a common failure mode because package lists, labels, base
images, and system dependencies drift over time.

Practical rule:

- rerun `hpccm` after any package-list or base-image change;
- regenerate again just before submitting the build job if the source changed;
- avoid hand-editing generated output unless that file is the canonical source;
- verify the final recipe and build inputs in the job output.

If the user already has `hpccm` locally, use that for regeneration. If not,
keep the regeneration logic inside a reproducible Slurm script rather than
building the recipe by hand on the login node.

## Build Pattern

Use the generic container helpers when the user needs a reusable template:

```bash
hpc write-container --kind generic <output-dir>
hpc install-container --kind generic --directory <remote-dir>
```

Use those helpers as a starting point for an Apptainer definition-file build
job, then fill in the project-specific recipe and labels.

If the build needs many packages, treat it like any other heavy install: use a
pilot job first, keep build artifacts off the login filesystem when possible,
and prefer node-local or scratch-backed temp space for temporary build files and
cache directories.

## Output

Report:

- whether a container is justified;
- whether the source recipe is handwritten or generated by `hpccm`;
- where the recipe and build outputs should live;
- whether the build should run in Slurm;
- what must be regenerated before the next build.
